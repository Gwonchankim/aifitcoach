# UI/UX 확정안 v2 — 원천 스펙 대조 결과 (2026-08-09)

> **입력**: 제품 오너 확정 프로토타입 7종(홈 / 온보딩 / 세션 / 기록 / 주간 프로그램 / 페이월 B / RIR 캘리브레이션).
> **이 문서의 성격**: 구현 전 대조 산출물. **코드는 아직 없다.** 승인 대기 항목은 §6.
> **왜 대조부터 하는가**: 파생 문서(`UX_STATES.md`)가 원천과 갈라져 evaluator 가 하드 게이트를 오판한 적이 있고,
> 스펙이 근거까지 적어 배제한 `datalist` 를 그대로 채택해 **iOS 에서 기능이 소멸**한 적이 있다(CLAUDE.md 함정 2).

## 0. 확정 전제 (제품 오너, 2026-08-09)

**[결정 A] "세 세션이 쌓이면 추천이 나타난다" = 확정 정책. 구현은 표시 계층 게이트.**
- `packages/shared/recommendNextSet` 와 `golden_tests.json` 은 **건드리지 않는다**. 골든 30/30 green 유지.
- 엔진은 지금처럼 계산하고, 노출만 막는다. 임계값은 상수 1곳 + ADR.
- 근거: "3세션"은 신뢰도 표시 정책이지 추천 수학이 아니다. 엔진에 박으면 `rules_version` 을 올려야 하고
  뮤테이션으로 쌓은 회귀 방어가 흔들린다.

**[결정 B] "추천 대상 무료 2종목"도 접근/표시 계층에서 게이팅.** 엔진은 순수 계산, 노출은 구독 상태가 결정.

> **설계 함의**: 게이트가 웹에만 있으면 오프라인 미러(STEP 6)와 화면이 갈린다.
> 게이트는 `packages/shared` 에 두되 **`recommend.ts` 가 아닌 별도 모듈**(예: `display-gate.ts`)로 분리해
> API·웹이 같은 판정을 쓰게 한다. 엔진 파일은 열지 않는다 → 전제 위반 아님. (**D-1** 에서 확정)

### 프로토타입 내부 모순 — 확정안끼리 충돌한다

| | |
| --- | --- |
| **M-1** | **"세 세션" vs "세 세트"**. 홈: "**세 세션**이 쌓이면 무게 추천과 추정 1RM이 나타납니다". 기록 탭: "**세 세트**가 쌓이면 다음 세션 추천과 추정 1RM이 나타납니다" / "세트를 3개만 기록해도 다음 세션 무게를 계산할 수 있습니다". 기록 탭 차트는 또 "**3회**부터 추이를 보여드립니다"(=세션 3회). → **결정 A 의 단위가 확정되지 않았다. D-1.** |
| **M-2** | **게이트 범위**. 결정 A 는 "해당 **종목** 완료 세션 < 3"인데, 홈 문구는 전체 3세션처럼 읽힌다. 페이월은 **종목 단위** 게이팅이라 종목 단위가 자연스럽다. |
| **M-3** | **스트릭 정의**. "연속 **11일** · 2완료 +1부분", "연속 12일 · 3완료". 11일에 완료가 2회면 "연속 운동일"이 아니다. 현재 `streak_days` 는 계획된 날 기준(ADR: 즉석 세션 제외). **무엇의 연속인지 불명.** |

## 3. 마일스톤 제안

### M-UI — 리스킨 (계약·엔진·골든 무손상)

**하나로 묶으면 안 된다.** "토큰 교체"와 "세트 행·RIR·⋯ 개편"은 성격이 다르다.
전자는 값 교체라 E2E 가 거의 그대로 살고, 후자는 **인터랙션 변경**이라 세션 E2E 를 대량 재작성해야 한다.
둘을 섞으면 회귀가 났을 때 색 때문인지 구조 때문인지 못 가른다.

- **M-UI-a 토큰·셸**: `globals.css` 값 교체(§7 매핑), 폰트 셀프호스팅, radius/테두리/터치 타깃.
  **인터랙션 불변** → 기존 E2E 가 회귀 그물로 그대로 작동한다. §3.1 대비 보정 포함.
- **M-UI-b 세션 인터랙션**: 완료행 1줄 축약, 완료 체크 48×48, 기존 RIR 단일필드(0~6/`null`) 유지,
  교체/통증 기록/삭제의 3항목 앵커 메뉴. 길게 누르기·화면 스테퍼·undo·건너뛰기는 제외한다. AC·UX_STATES 개정과 함께.
- **제외**: 오프라인 배너(R-19 — 큐가 없다), 페이월, 기록·프로그램 탭 데이터, **4탭 IA 셸(D-2: M-4′ 직전 별도 티켓)**.

### M-4′ — 기록 탭 · 주간 프로그램 탭

- `/analytics` 3종 개방 + **집계 계층 신설**(`Estimated1rm`·`MuscleWeeklyLoad` 를 실제로 채운다 — 지금은 미사용 모델).
- 12주 수명주기(R-03), 주간 볼륨 권장 범위(R-24), 세션 상세(계획 대비 실제), 종목 추이·공백 끊김.
- 선행 결정: R-11(재배치), R-21(backfill).

#### Sprint 0 계약 잠금 (D-32~D-44, 2026-08-16)

- 집계는 수행기록 원본 + targeted recompute/조회 reconcile/전체 rebuild가 같은 projector를 쓰는 hybrid다.
- e1RM·PR은 저반복 우선 + RIR 보정 공용 공식으로 통일하며 기존 raw-Epley projection은 rebuild한다.
- 프로그램은 lifecycle 메타만 저장하고 12주 세션을 사전 생성하지 않는다. 실제 저장소에는 기존 설명의
  `generation_input`/`planWeek`가 아직 없으므로 신규 입력 보존과 레거시 template fallback을 구분한다.
- 표시 게이트 파일은 `packages/shared/display-gate.ts` 하나다. 서버가 게이트한 응답이 온라인 권위이고,
  오프라인 mirror만 같은 모듈을 사용한다.
- T-UI-3만 projector와 병렬 가능하다. 일정 재배치·수동 과거 기록 입력·스트렝스 임의 범위는 제외한다.
- 상세 계약과 red proof 기준은 `M4_CONTRACT.md`가 소유한다.

### M-7′ — 페이월 · 구독 · RIR 캘리브레이션

- R-02·R-05·R-06. `TEST_SCOPE.md` 의 "결제 보류" 해제 여부가 선행(**D-9**).
- 캘리브레이션은 결제와 독립이라 **먼저 뗄 수 있다**(R-06 은 추천 정확도에 직접 기여).

### 순서 — 근거 있는 제안

```
[선행] 테스트 격리 + E2E 요일 의존   ← 협상 대상 아님
   ↓
M-UI-a (토큰·셸)
   ↓
M-UI-b (세션 인터랙션)
   ↓
STEP 6 (오프라인 동기화)
   ↓
M-4′ (기록·프로그램 탭)
   ↓
M-7′ (페이월·구독)   ※ RIR 캘리브레이션은 M-4′ 와 병행 가능
```

**왜 테스트 격리·요일 의존이 먼저인가**
지금 E2E 는 **월·수·금에만 전량 통과**한다(토요일 실측: 17 failed / 22 미실행).
이 상태로 전 화면을 리스킨하면 회귀를 잡을 그물이 주 3일만 존재한다.
격리까지 고쳐야 리스킨 중 매일 돌릴 수 있고, 그때부터 E2E 가 실제 방어선이 된다. **UI 작업 착수 전 필수.**

**왜 STEP 6 가 M-4′ 보다 먼저인가**
프로토타입의 "기기에 저장됨 / 저장 대기 / 저장 실패 · 지금 다시 시도"와 앱 재시작 복구는 **오프라인 큐가 있어야 의미가 있다**(R-19).
큐 없이 배너만 그리면 사용자에게 거짓을 말하는 UI 다. 기록 탭도 마찬가지 — 헬스장에서 안 보이는 추이는 반쪽이다.
M-UI-a/b 에서는 **배너를 넣지 않는다**(빼는 게 정직하다).
